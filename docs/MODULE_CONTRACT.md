# In-process module contract

Defined before implementation: `heart-contract` owns `Capability`, `Module`, `ModuleResult`, `Source`, and `Outcome`. The core registers arbitrary modules and sees only their declarations and results. CLI wiring chooses the installed modules; core never imports them.

A capability declares a unique `id`, description, JSON object input schema, default authored progress text, and an optional `command` declaration (`name`, optional `argument`). Milestone schemas support object properties of string type, required fields, length limits, and reject additional properties. Registration validates every schema property, including absent optional fields, and rejects unsupported keys and malformed constraints. Argument lengths count the raw string’s Unicode characters (default maximum 4096); positive minimum length also rejects whitespace-only values. Core validates a model's selected ID and arguments before invocation. Modules validate again at their boundary. No module result can invoke a capability.


Commands are declared by modules and registered generically. Command names use nonempty lowercase ASCII letters, digits and hyphens; duplicates and built-in names (`help`, `exit`, `quit`, `profile`) are rejected. A no-argument command requires an empty input schema. An argument binding must name the capability's only string property, which can be required or optional. This deliberately supports one literal remainder, rather than a flag parser or guessed bindings. CLI help is generated from these declarations. Current declarations are `/disk [path]`, `/system`, `/uptime`, `/search <query>`; core has no capability-ID branches.

`Engine::invoke` parses explicit commands, trims the remainder's outer whitespace, preserves internal spaces, leaves quote characters literal, and validates the original module schema before execution. Omitted input produces `{}`; required input must be supplied. Unknown/malformed commands invoke no module or inference (including retention). No argument normalization, shell expansion or LLM routing occurs. Execution shares the same result/phrasing/fallback path as the opt-in experimental `Engine::ask` API.

`Module::execute(arguments)` returns an envelope: `outcome` (`success`, `needs_input`, or `error`), `fallback` (direct factual text), optional canonical `factual_text`, optional display-ready `template_fields`, optional JSON `data`, and `sources` (`title`, HTTP(S) `url`). `factual_text` defaults to absent for existing envelopes; when present it contains the exact canonical excerpt, without presentation labels. Core sends only this canonical text as phrasing evidence and uses it for numerical/unit/negation checks, otherwise using `fallback`. The request remains a separate data field. Structured `data` and source metadata remain in the common envelope for consumers and do not enter model input. Labels must not add factual claims. Errors are user-safe strings; raw transport/provider errors and credentials never enter the envelope.

Example: declaration `{"id":"web.search","inputs":{"type":"object","properties":{"query":{"type":"string","minLength":1,"maxLength":400}},"required":["query"],"additionalProperties":false}}`; arguments `{"query":"Amsterdam temperature today"}`. Success may carry fallback `Example report: 12 °C.`, data `{"results":[...]}`, and a source URL. Missing credentials return `needs_input`, never success.

Retrieved text is untrusted evidence. The search module returns a short attributed excerpt, not an independently verified synthesis. Selection stays inside the web module: all non-generic query subject tokens and a substantive declarative predicate or stricter factual answer signals must occur within the same short sanitized sentence with terminal punctuation. General declarations require the subject before a copula; planned, conditional, future and negative statements decline. The module can select later sentences or candidates, ignores provider scores, and retains only eligible sources with the same ordering in `data.evidence`. Canonical text and `Source [1]` fallback cite the first retained source. No qualifying evidence returns Error with no sources/canonical text, so no generated answer follows. This lexical filter cannot prove semantic relevance or factual correctness and may decline valid paraphrases, abbreviated names, cross-sentence answers and question forms without recognized answer evidence. Current-temperature signals cannot establish actual freshness. The common contract and core have no search-specific rules. Final generation permits a short grounded paraphrase in the chosen character, with instructions to minimally edit factual vocabulary, add brief character wording, copy numeric values/units exactly and avoid calculations, conversions, rounding or answers from outside knowledge. Character instructions are trusted system text, separated from the request/evidence payload; profile JSON can supply a light authored suffix with marker words suppressing a duplicate; the bundled butler preserves its honorific and cat has no suffix. The complete generated answer passes the guard, so generated suffix metadata cannot append unchecked claims. Core checks response shape/length, lexical grounding, numerical tokens, negation (including common English contractions) and units. Numeric comparison permits exact ASCII thousands grouping and trailing decimal zeros without floats, value tolerance or conversions. Validated numeric fragments do not add votes to lexical scoring; concise numeric replies require every accompanying text token, including short units, to occur in canonical text. It preserves signs and scale, keeps unsupported numeric spellings literal, and distinguishes disk GiB, GB, byte and bytes; unsupported Unicode numeric/sign forms conservatively use fallback, links remain separate and cannot be supplied by the model. Failure returns the exact factual fallback. Web fallback uses `Source [1] excerpt:` followed by the selected short sentence (at most 260 characters); the title appears only in the original source list. Safe typed phrasing status distinguishes accepted, timeout, inference failure, malformed output and deterministic rejection categories. With `--diagnostics`, the console prints these categories/timing to stderr and the dashboard displays them in dialogue; it never logs candidates, prompts, evidence or provider error text. These checks reject common unsupported changes but do not prove semantic fidelity, completeness, or relevance. Live evaluation must inspect unsupported claims, omissions, changed relationships and negation; a prompt alone is not verification.

Current-request context only. The inference trait supports selection, selected-only extraction, phrasing and explicit model retention. Explicit invocation makes zero selection/extraction calls and at most one successful-result phrasing call; successful results opting into authored templates make zero inference calls. Experimental routing makes at most two routing calls plus that phrasing call, without retries. `Reply.routing_performed` distinguishes these paths; explicit replies have zero selection/combined timings and absent extraction timing. Safe diagnostics report selection and optional extraction timings separately; combined routing timing sums their inference durations and counters. Ollama uses JSON schemas, non-streaming responses and `think:false`; no implicit model downloads or cloud fallback. Retention uses a ten-minute active lease (longer than bounded request stages), reset to the configured idle period after any attempted inference, including inference error exits. Explicit module errors and authored results, including missing/invalid-template fallback, attempt neither inference nor retention and preserve the existing idle state. Experimental routing still resets retention because routing attempted inference.


`heart-system` supplies three independent implementations through this same contract. `system.disk_space` has optional `path` (string, 1–4096 raw characters), `required: []`; omitted path uses the process working directory. `system.info` and `system.uptime` use empty `properties` and `required: []` and accept exactly `{}`. Core validates these schemas without knowing any module ID. Routing first selects only an opaque registered capability ID or null using the complete request and IDs/descriptions. Core independently rejects missing, malformed or unknown selections before continuing; null stops without extraction or execution. For nonempty inputs, a second inference call receives only the original request and selected projected declaration, and returns that input object directly. It cannot change the selected capability. Empty-input declarations skip extraction and supply `{}` through the same validation boundary. Runtime validation still checks the original selected module schema before any execution. For inference only, core projects every optional string property to a required nullable string, preserving length bounds, and uses that same projection in the capability metadata and generation schema. The model must supply exact literal user text or JSON null for an unspecified optional value; it must not resolve or normalize values or fill in defaults. Core independently rejects missing/unknown wire fields and invalid values, removes only declared optional nulls, then validates the original module schema. Modules continue to receive strings or absent properties, never these null sentinels, so their optional/default semantics remain unchanged. Required strings keep their original shapes; empty-input capabilities need no extraction output. CLI installs the implementations and discovers runtime JSON profile progress; system code has no provider, network, inference or shell dependencies.

Native success envelopes provide identical canonical `fallback`/`factual_text`, structured `data` and empty `sources`. Disk data has canonical resolved UTF-8 `path`, `total_bytes`, `free_bytes`, `available_bytes`, `used_bytes` (checked total minus free) and `reserved_bytes` (checked free minus available). All counters come from one path-specific `fs4::statvfs` call; saturated `u64::MAX` or inconsistent counters fail safely. Canonical text includes the quoted resolved path; terminal controls and unsafe canonical display paths are rejected. Relative paths and symlinks resolve explicitly, with no home/variable/glob/shell expansion. No files are created or changed by module execution.

APFS may report shared-pool counters through this API; `used_bytes` is not necessarily `df`'s exclusive per-volume Used value. Historical actual-model checks showed optional path arguments being omitted despite the user explicitly specifying a path. The inference-only projection addresses that representation without changing the module default; follow-up acceptance is recorded separately. Runtime validation still cannot establish whether an argument was faithfully extracted: a syntactically valid route may omit a supplied value via null, invent a value, or select the wrong capability. Actual-model checks must compare literal module arguments and outcomes separately.

System data has nullable `os_name`, `os_version` and `architecture`; unavailable/unsafe OS metadata is null, never a guessed kernel/product substitution. `sysinfo::System::cpu_arch` normally reads native machine architecture, but internally falls back to the compiled HEART target when unavailable and does not expose the source. Uptime data has `uptime_seconds` and readable `duration`. Linux uses static `System::uptime` (`/proc/uptime`, then native sysinfo; zero is ambiguous). macOS checks static `System::boot_time` and subtracts it from current UNIX wall-clock seconds, returning error for zero/missing or future boot time rather than presenting epoch-sized uptime after a failed native read. Both include suspended time; macOS wall-clock adjustments can affect the result. No broad `System` instance or refresh is created. Errors use safe generic text without raw OS errors or failed-path echoes.


Profiles are trusted local presentation configuration loaded at startup, with `--profiles-dir` selecting the directory. They contain stable `id`, `instructions`, `greeting`, `status`, optional capability-ID `progress` overrides and optional `templates` keyed by capability ID and optional `presentation` (`suffix`, `markers`). CLI rejects profile IDs colliding with built-in/module commands or another profile. `/ID` and `/profile ID` select discovered profiles without source changes. Final generation receives profile instructions in system text, the request and canonical module text in separate user data fields; profile content never authorizes capabilities or modifies guard vocabulary. Custom generated style words outside the fixed allowlist may cause exact fallback. Authored template prose is trusted and does not use this lexical guard or generated suffix processing. See README for the schema example and restart behavior.


Optional profile `appearance` is frontend-neutral metadata for dashboard colors and a builtin portrait asset. It contains no TUI types and changes no module contract, prompts or authority. Old profiles without it use a neutral frontend theme; invalid assets/colors fail profile loading. Both frontends share command classification/execution. Dashboard system/music widgets are labelled mocks and never call modules; only user-submitted requests enter the existing engine.

Successful results may supply optional `template_fields: map<string, string>` in the common envelope. Presence (including an empty map) selects deterministic authored presentation; absence retains generated phrasing. Core uses only the opaque capability ID to find `profile.templates[id]`. Missing or invalid templates return the exact fallback without generation. Error/NeedsInput outcomes ignore fields. Serialization omits absent fields and deserialization accepts older envelopes; existing JSON profiles without templates remain valid.

Templates use `{name}` with nonempty ASCII letters/digits/underscores, starting with a letter or underscore. Each occurrence copies its named display-ready value literally, without recursively interpreting braces inside values. Repeated placeholders work. Unknown/missing names, unmatched/nested braces and unsupported syntax fail closed. No expressions, formatting directives, calculations, unit conversion, brace escaping, shell expansion, loops or conditionals exist. Templates and output are bounded to 8192 UTF-8 bytes; blank output, control characters, Unicode line/paragraph separators and directional override/isolate controls are rejected. Only syntax/output shape are checked: trusted authored prose is not semantically verified. Diagnostics distinguish `Authored`, `AuthoredFallback` and generated `Accepted`; no authored reply has a phrasing timing. Original sources, data and canonical text are preserved.

`system.disk_space` supplies `available`, `used`, `total`, `free`, `reserved` as already formatted two-decimal GiB strings, and `path` as the safe JSON-quoted canonical path. Canonical fallback uses the same quantities and path strings. `system.uptime` supplies `duration`, exactly matching its canonical/native duration formatting and structured `duration`; raw bytes/seconds remain available. OS info and web search omit `template_fields`. A custom pirate profile can set `"templates": {"system.disk_space": "Arrr, {available} available on the filesystem containing {path}.", "system.uptime": "Running for {duration}, matey."}`; restart reloads profile files. Future modules can opt in through the same generic contract without core branches.

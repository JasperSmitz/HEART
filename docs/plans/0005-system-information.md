## Acceptance criteria

1. Add a separate `modules/system/` workspace crate exposing three capabilities through the existing common `Module` contract: `system.disk_space`, `system.info`, `system.uptime`. Multiple small Module implementations in one crate are sufficient; do not redesign the registry or add module/provider branches in core. CLI registers the capabilities and authored progress for both built-in profiles.
2. Disk space accepts an optional string `path`. Omitted path means the process working directory, clearly documented and identified in the response as the filesystem containing the resolved path. Existing files or directories may select their filesystem; relative paths resolve against the working directory, symlinks resolve explicitly. Do not guess named drives, enumerate directories, calculate folder sizes, or scan all disks. Missing/inaccessible/invalid paths return safe honest outcomes. No shell expansion or execution; document supported path syntax. Home expansion is optional, limited to `~`/`~/` if implemented, never arbitrary variable/glob expansion.
3. Return structured bytes for total, free, available-to-user and used space, with checked arithmetic. Used means total minus free, not total minus available. Reserved/unavailable capacity can make used plus available differ from total. Human text uses correctly named units (GiB if binary), identifies the checked path, and includes available/used/total without pretending to measure directory contents. Prefer one native filesystem snapshot via a safe wrapper. No file creation or elevated permissions in application behavior.
4. System basics reports OS name/version when available and architecture, with structured fields and honest missing-value handling. Do not silently substitute a kernel version as a macOS product version, expose hostnames/usernames/serials, inspect processes, or collect CPU/RAM telemetry. Uptime returns elapsed seconds since system boot plus readable duration; document the platform API semantics and any inability to distinguish unsupported zero from legitimate zero.
5. Local outcomes use existing success/needs-input/error envelopes, canonical fallback/factual text and structured `data`; `sources` is empty because these are native readings. No provider/network/LLM logic inside system module. Normal terminal questions select the correct registered capability; author/module facts stay unchanged through accepted phrasing or exact fallback. Validate both module inputs and generic routing, including web versus local selection, without extra research loops.
6. Use purposeful dependencies with scoped features and safe native APIs, avoiding model-generated shell commands or a bespoke portability framework. Suitable reviewed options are `fs4::statvfs` for path-specific filesystem snapshots and static `sysinfo::System` OS/uptime functions; the developer may select a comparably simple approach and explain it. Never instantiate broad CPU/process/memory refreshes merely to read static metadata. Preserve existing module and inference behavior.
7. Meaningful tests cover path/default/relative/symlink/error behavior, byte semantics including reserved space and overflow/inconsistent readings, missing OS values, uptime formatting, empty sources, schema/argument validation, and local/web routing without live credentials. Run formatting, warnings-denied Clippy and workspace tests on macOS, plus Linux tests in the existing container engine where practical. Verify native results against independent platform readings within sampling tolerance; test at least one actual Mac path. Add a small reproducible smoke/evaluation route for live local-model selection against real system modules and a counted web stub, so no Tavily calls or keys are needed. Root owns final live checks and evidence.

## Acceptance discovery — route/schema binding

The first 2B live run selected the expected capability ID in 9/10 cases but only invoked the expected module in 5/10; five calls were blocked for invalid arguments, and one invoked a malformed literal path. This exposed an existing generic schema weakness: capability IDs and the union of argument shapes were constrained independently. The original observations are retained in `docs/evaluations/system-information-initial.json`.

Correction round 1 authorizes a generic route-schema union that binds each ID to its own argument object, retaining core's fail-closed validation and the existing capability/arguments shape. No provider-specific branches, extra model calls or default-model changes. Omit optional arguments the user did not supply; explicitly document that an omitted disk path selects the working directory. Recheck fixture/schema capture assumptions and actual local-model behavior. This necessary integration correction supersedes the initial expectation that core would need no changes; the module boundary remains generic.

The union rerun selected the first disk branch in all ten cases. Correction round 2 preserves JSON property insertion order, emitting capability before arguments, with a regression on the serialized schema. Final 2B and 4B runs each selected all ten correct capabilities and invoked the expected module exactly once, but both ignored explicit `/` in two cases. Actual CLI probes also ignored quoted/unquoted `/private/tmp` and a nonexistent path. Optional-argument intent fidelity remains unresolved; this is not a completed acceptance criterion or a reason to silently change the default model.

The natural-language explicit-path part of criterion 5 is unmet even though direct module arguments work. The reviewer confirmed this as a medium-severity acceptance finding. Both models exhibit it; no verified quoting workaround was found. Native capability selection, default-path readings and system basics/uptime worked in the final controlled sample. This does not establish general routing or semantic reliability; native factual fallback remained frequent.

Full results and preserved initial/union/final runs: [system-information evidence](../evaluations/system-information.md). No Tavily calls, model downloads, global settings, dashboard/telemetry/profile changes or commits were made. Developer/reviewer were requested as Sol/medium; runtime selection was not independently observed. The existing user-owned Ollama service remains running; tested models were unloaded.

Recommendation to the user: authorize a separately scoped optional-argument routing investigation/fix before marking this milestone accepted or moving to dashboard implementation.

# Lessons

Reviewer-owned evidence log. Add an entry only for a substantial discovery that should affect future work; do not invent lessons or record routine status. The reviewer may edit this file only. The architect decides whether a lesson should become a project convention.

Use a short dated entry with:

- **Discovery:** what happened, with concrete evidence or a reference.
- **Why it matters:** the observed impact or recurring risk.
- **Future action:** a specific practice to apply or evaluate.

## 2026-10-19 — Exercise ordinary language and Unicode in factual guards

- **Discovery:** Independent compiled-API checks found that the initial phrasing guard accepted `The museum isn't open on Monday` rewritten as `The museum is open on Monday`, and accepted `Amsterdam is −12 °C` against a `12 °C` fallback. Its tests covered standalone `not` and ASCII digits, while contractions and the Unicode minus sign bypassed those checks. The initial twelve live model fixtures preserved their facts, so their success did not expose these boundary failures.
- **Why it matters:** Token checks can miss direct factual reversals even before the broader, acknowledged problem of semantic equivalence. A successful small model evaluation cannot substitute for adversarial tests of the deterministic rejection boundary.
- **Future action:** Include contractions, typographic apostrophes, Unicode signs and digits, and raw-versus-normalized text in regression cases for factual and input-validation guards. Reject unsupported forms conservatively when faithful normalization is unavailable, and continue to describe the checks as filters rather than semantic verification.

## 2026-10-19 — Bind capability choices to their argument schemas

- **Discovery:** The first system-information live evaluation selected the expected capability ID in 9/10 cases, but five routes supplied arguments belonging to other capabilities and were blocked before execution ([preserved observations](evaluations/system-information-initial.json)). The generic routing schema independently constrained capability IDs and a union of argument objects, so it allowed those invalid pairings. Fixed-route tests passed because they supplied valid pairs directly. Correction round 1 changed the schema to a union of complete routes, each binding one ID to its declared inputs, while retaining boundary validation.
- **Why it matters:** Correct capability selection alone does not establish a working request. Adding capabilities with different input shapes exposed a schema weakness that a single-module setup and injected-route tests did not exercise; runtime validation prevented invalid execution but left ordinary requests unanswered. The first union-schema rerun then selected the first branch's disk capability in all ten cases ([observations](evaluations/system-information-union.json)): syntactically bound arguments still did not establish correct intent selection. Its serialized branch properties placed arguments before the capability discriminator; round 2 preserves discriminator-first order, with a regression on serialized schema text.
- **Future action:** When adding a distinct capability input shape, verify complete ID/argument pairs and serialized discriminator order in the generated routing schema, then run actual-model acceptance cases alongside deterministic dispatch tests. Keep runtime validation independent of generation constraints, and report route identity, valid arguments and module outcome separately. Treat structural checks and serialized-order fixes as implementation evidence; actual-model results must establish intent-selection behavior.

Follow-up evidence from [plan 0006's 2B correction checks](evaluations/optional-argument-acceptance-2b-round2.json): required nullable inputs and prompt corrections improved explicit-path extraction, omitted-value defaults and unsupported-operation rejection, but both weather searches then invoked unrelated native capabilities; the second correction also changed literal `.` to `/` in one case. The same structurally valid boundary accepted those routes. A prompt change can move failures between capabilities rather than resolve routing fidelity. Recheck the unchanged complete capability/argument/outcome matrix after each correction, preserve failed runs, and enforce the correction limit instead of accepting success on only the targeted examples.

The authorized [two-step experiment](plans/0007-two-step-routing.md) isolated selection from extraction without establishing semantic fidelity: [2B](evaluations/two-step-routing-2b.json) passed 14/20 regression cases and 2/4 additional wording cases, while [4B](evaluations/two-step-routing-4b.json) passed 18/20 and 4/4. 2B dropped explicit `/` and `.` to null and still selected unrelated read-only capabilities; 4B invented `./` or the literal string `null` for omitted paths. All are valid input shapes, so the independent boundary correctly could not reject them. Decomposition made the failing stage observable and its measured warm overhead was small, but did not itself improve acceptance. Preserve literal, default and unsupported-operation checks when comparing another model or design; do not infer correctness from stage isolation, matching canonical paths alone, or a successful latency target.

## 2026-10-20 — Inspect rejected candidates and test interacting factual guards

- **Discovery:** [Initial phrase-rejection observations](evaluations/phrase-rejection-initial.json) showed the model turning raw byte counters into `802.79 GiB` despite the supplied canonical `747.66 GiB`; the number guard correctly rejected that changed value. Independent validator probes also found that comma-separated `24,901` was split into smaller allowed numbers and equal-valued GiB-to-GB changes passed the unit guard. After those fixes, concise equivalent answers such as `24,901 miles.` → `24901 miles.` and `747.660 GiB.` → `747.66 GiB.` still failed lexical grounding: it counted numeric spelling fragments as unsupported words. Longer tests with shared surrounding wording hid that interaction. Correction round 1 separates already-validated digit fragments from lexical scoring and preserves rejection of invented words and units.
- **Why it matters:** A fallback does not reveal whether the model changed a fact or a deterministic filter rejected harmless formatting. Supplying both raw and canonical quantities invites unnecessary recomputation, while fixing one validation stage can leave another stage rejecting the same faithful answer.
- **Future action:** Preserve original rejected candidates in explicit local evaluations; distinguish genuine changed values from guard false positives. Give phrasing a single canonical factual representation while retaining full structured results for consumers. Check exact numeric normalization through the complete validator using concise answers, large integers, malformed groups, signs, unit changes and invented vocabulary; do not rely on padded examples or numeric tokens alone.

## 2026-10-20 — Test answer evidence separately from search success

- **Discovery:** [Plan 0011](plans/0011-web-evidence-relevance.md) replayed preserved provider responses through the production selector. The [initial replay](evaluations/web-relevance-replay-initial.json) selected Python's originally planned release date instead of its actual release date; independent fixtures also accepted period-terminated question headings and an Earth-size sentence whose only number was a page reference. Two correction rounds added explicit rejection signals and local measurement checks; the [final replay](evaluations/web-relevance-replay.json) preserves the resulting selections and declines.
- **Why it matters:** HTTP success, provider rank, titles and shared subject words do not establish answer evidence. A selected excerpt can still omit the requested relationship or completeness, while stricter checks can reject useful paraphrases or answers split across sentences. Canonical text, fallback citation and retained source/data ordering must also agree after filtering.
- **Future action:** Replay fixed provider captures through the actual selection path, supplement them with concise no-answer counterexamples, and check both selection and citation alignment. Preserve false positives and false negatives separately; describe lexical signals as a bounded filter rather than semantic verification, and return broader relevance tradeoffs to discussion after the correction limit.

Diagnostics are safe typed categories/timings in dialogue, never writes over the screen.

Profiles add optional plain `Appearance` metadata: validated builtin asset key/display name plus hex semantic colors. No TUI type enters core; profile instructions, greetings, progress, presentation and templates are preserved. Old custom profiles use neutral frontend styling. Dialogue uses display names while retaining the submitting profile's label on asynchronous results. Input editing uses UTF-8 byte boundaries and rendered column widths; focus excludes hidden mock music. Known Ghostty/Kitty terminals with nonzero OS-reported cell pixel dimensions use Kitty graphics; unknown terminals, multiplexers, unavailable metrics and `HEART_PORTRAIT=text` use a labelled text fallback. No stdin capability probe runs. Nearest-neighbor contain scaling preserves proportions; the decoded source and a single encoded size are cached, with one image ID reused on resize. Kitty virtual placements follow the rendered cells, help suppresses portrait output, and shutdown frees the owned image. Other character asset keys currently use text fallback; additional artwork/expressions remain future work.

Ratatui's restoring panic hook and an additional guard restore terminal state on exit/errors; non-TTY launch is rejected before engine construction. Bracketed paste protects pasted newlines from submission where supported. Unicode, exact RGB and graphics support remain terminal-dependent; fonts remain user-controlled. ## Embedded terminal workspace

[Plan 0014](plans/0014-embedded-terminal.md) adds one manual shell to the dashboard; verification and independent review are recorded in [its evaluation](evaluations/embedded-terminal.md). [Plan 0015](plans/0015-shell-first-layout.md) refines this into a full-height left workspace beneath the header, with System, Music, compact JRPG dialogue/real portrait and HEART input in the right sidebar. Utilities remain mocked; small layouts hide them and reduce companion space first. One `render::areas` calculation determines both visible shell bounds and parser/kernel PTY dimensions. The shell retains its actual cursor coordinates, including normal initial prompt placement and scrolling at the bottom after output fills the screen. Preview construction creates screen state only, without opening a PTY or starting a shell.

`crates/cli/src/dashboard/terminal.rs` owns the PTY, child, bounded background I/O and parsed terminal screen. It imports no engine, capability or assistant request type. Only manually routed key/paste events reach its writer; generated protocol replies are terminal housekeeping, not shell commands. The existing assistant worker owns no terminal handle. The no-flag CLI and capability registry remain unchanged.

`portable-pty` 0.9.0 creates a controlling PTY/session and starts interactive `$SHELL` in the current directory. Ordinary environment/rc/PATH/ZDOTDIR/Starship configuration is inherited. The inner terminal advertises `xterm-256color`, removing outer Ghostty/Kitty and multiplexer identity/size hints. Thus opening a dashboard now deliberately starts the user's shell and its configured startup commands, while widgets/rendering still invoke no assistant module, model or provider.

`tui-term` 0.3.4 renders its re-exported vt100 0.16.2 screen. Scrollback is bounded to 2,000 rows; I/O queues are bounded, and each frame processes at most sixteen 4 KiB chunks. Nonblocking Unix file descriptors and background reader/writer threads keep child output and stalled input from blocking UI interaction. CSI device/cursor reports are answered locally; unsupported OSC/DCS/APC/PM strings are discarded incrementally rather than forwarded or accumulated. A narrow existing-parser callback maps standard HVP cursor positioning (`CSI row;col f`) to supported CUP (`H`), including fragmented reads, which fixes btop without a separate emulator. Fonts and shell configuration files are untouched.

Shell focus is the default. F12 globally toggles shell/HEART input; ordinary shell keys, including Ctrl+C/Q, Tab and F1/F2, go to the child. HEART shortcuts are contextual. Shift+PgUp/PgDn inspect host-managed shell scrollback; typing returns live. ANSI colors, application cursor mode, bracketed paste, cursor visibility and alternate-screen state come from the parser. Shell EOF/start failure leaves HEART controls available without automatic restart. Compact companion text retains the latest answer; focusing dialogue exposes bounded prior assistant lines.

Unix shutdown validates foreground attachment through the owned PTY, terminates that job with bounded HUP/TERM/KILL escalation before stopping/reaping the shell, and excludes HEART's own group. It does not require the foreground group's original leader PID to remain alive. The writer uses an owned duplicate wrapped in `File`, avoiding portable-pty's Unix writer destructor that sends newline/EOF; dropping it never submits pending text. A documented temporary unsafe fd borrow is limited to duplication while the master is alive. Both shutdown cases have real-PTY regressions and independent rechecks. Guarantees cover the owned shell and attached foreground job, not deliberately detached daemons. This integration remains bounded by the parser/widget's compatibility, not Ghostty's full emulator feature set; mouse passthrough, child graphics/OSC clipboard and extended keyboard protocols are not implemented. Actual macOS runtime validation remains outstanding.

## Capability and inference boundaries

The [web evidence refinement](plans/0011-web-evidence-relevance.md) is implemented and independently reviewed, with 66 tests passing on macOS/Linux ARM64. It mitigates the reported wrong-topic class using module-local lexical checks and coherent later-excerpt selection; general answer relevance remains unverified. The [comparison and replay](evaluations/web-evidence-relevance.md) preserve valid declines and remaining same-subject false positives. Tavily basic remains the production mode; no provider replacement or core/contract change occurred.

The explicit-command/profile pass is implemented and independently reviewed: all 47 final all-target tests pass on macOS and offline Linux ARM64. A bounded native CLI smoke confirmed literal/default paths, zero routing calls, one phrasing call per success and safe fallback; a follow-up confirmed module Error/NeedsInput results make zero model requests. See [acceptance evidence and limits](evaluations/explicit-commands.md). Historical natural-language routing acceptance remains separate and unresolved.

Modules declare IDs, descriptions, a deliberately small JSON object schema, authored default progress and optional slash-command metadata. Core validates command uniqueness/reserved names and binds either an empty schema or its single string property to the literal remainder. Explicit invocation validates original inputs without selection/extraction inference. Unknown/malformed commands invoke nothing; omitted optional input remains absent. CLI help is declaration-driven. Core has no imports or branches for installed modules/providers. Runtime JSON profiles supply character progress overrides keyed by opaque capability ID. Core rejects unsupported/malformed schema declarations at registration, then validates raw argument lengths and model routes before invoking exactly one registered module, then treats its common result as data. The initial transport is in-process Rust traits; no dynamic loading or MCP.

Experimental routing first selects an ID or null using only the request and capability IDs/descriptions. Core validates selection shape/type and registered ID before extraction. A nonempty-input capability gets a second local call with only the original request and selected projected declaration; the output is its input object, not another route. Empty-input capabilities skip extraction; null selection stops without execution. Optional module strings become required nullable inference fields. Strict conversion requires every declared field, removes only optional nulls and validates against the unchanged original module schema. These structural boundaries do not prove intent fidelity: a model can omit a supplied value via null or select an unrelated capability. No module-specific parsing or retries were introduced. The former union/discriminator-order approach and failures remain recorded in plan 0006; JSON insertion-order preservation remains enabled.

`Reply.selection_timing` and optional `extraction_timing` separate routing stages; `route_timing` sums their inference timings and counters. Opt-in CLI diagnostics expose those safe timings without prompts or model candidates. Explicit commands make zero routing calls and at most one successful-result phrasing call (zero for authored results); `Reply.routing_performed=false` distinguishes their zero selection/combined timing and absent extraction. Experimental requests make at most two routing calls plus one successful-result phrasing call. The local-only smoke example records all stages even on an early error, counts module invocations and checks literal arguments/outcomes for twenty original and four predefined wording cases.

Tavily requests use basic search, `auto_parameters=false`, `include_answer=false`, three results, no raw pages, one call and no retries. The module bounds response size and excerpt budgets, filters HTTP(S) sources, removes terminal control characters, and returns safe credential/quota/timeout/no-evidence failures. Its web-only selector tests all query subject tokens plus a substantive declarative predicate or stricter answer signals within a short sentence of each sanitized snippet; later eligible candidates/sentences can supply the answer. Provider scores and source titles do not supply relevance. Eligible sources retain provider order and matching structured evidence order, so fallback `Source [1]` and canonical factual text refer to the first retained source. No eligible sentence yields a safe Error, which skips phrasing. Selected sentences require terminal punctuation, and uncertain/planned/conditional/future/negative statements decline. Generic declarations require subject words before a copula and a substantive predicate; release-date checks require explicit release wording and a four-digit year; supported other signals cover composers, capitals, package managers, physical measurements, explicitly current temperatures and inline-code instructions. These lexical tests can reject broad or weakly evidenced questions, valid paraphrases, abbreviated names, long sentences and cross-sentence answers. They do not verify relationships, truth, completeness, date freshness or current conditions; no LLM classifier, extraction, page requests or retries are added. See [plan 0011](plans/0011-web-evidence-relevance.md).

System readings use a single safe path-specific `fs4::statvfs` snapshot and static `sysinfo` OS/architecture/boot APIs, with no process/CPU/memory refresh, shell commands or network dependency. Structured bytes distinguish available, free, used (total minus free) and reserved (free minus available), with literal canonical paths and safe error outcomes. APFS may report shared-pool rather than exclusive volume accounting. OS names are API-reported (`Darwin` on the tested Mac), product version is separate, and architecture has a documented compiled-target fallback. macOS uptime rejects unavailable boot time before wall-clock subtraction. Native sources are empty; disk and uptime supply display-ready fields for authored presentation, while OS info retains generated canonical phrasing. Structured byte/second data and canonical text remain available unchanged.

Ollama is a separate local service behind the inference trait. Non-streaming `/api/chat` requests use JSON schemas, `think:false`, 4096 context tokens, 384 output tokens, 30-second warm and 120-second cold deadlines, plus a three-second connect timeout. Each inference call sets a ten-minute active lease, safely beyond the combined request deadlines, so abrupt process exit cannot retain the model forever; a separate empty `/api/generate` resets the configurable idle lifetime after completion/error of requests that attempted inference. Explicit module errors and authored results (including template fallback) skip inference and retention entirely, preserving any existing idle lease. Failed idle reset preserves a successful answer, reports a warning, and attempts immediate unload. Requests after the idle interval get the cold deadline again. HEART never downloads a model or switches to cloud inference automatically.

Final phrasing receives trusted character instructions in its system prompt; the current request and canonical module text occupy separate user payload fields. Canonical text is `factual_text` when present, otherwise `fallback`; structured `data` and source metadata are excluded from model input. The prompt requests minimal edits retaining factual vocabulary and brief character wording, with exact numeric values/units and no calculations, conversions, rounding or outside-knowledge answers. Profile presentation metadata preserves the butler's short authored honorific without another model call; cat wording has no forced signoff. The complete generated answer passes the factual guard, including any suffix. Length/shape, lexical grounding, canonical numerical tokens, units and negation are checked; URLs remain outside generation. Optional common `factual_text` separates canonical excerpt text from fallback labels/titles; absent values retain fallback-based checks. Numeric comparison normalizes only unambiguous ASCII thousands grouping and trailing fractional zeros, without floating-point arithmetic, value tolerance or unit conversion. Validated numeric fragments are excluded from lexical scoring; concise numeric replies require all accompanying text, including short units, to match canonical tokens. Signs, exponents, attached units and malformed groups retain literal matching; leading decimal points cannot disappear. Disk units include distinct GiB, GB, byte and bytes checks. Common negation contractions are checked, and unsupported Unicode numeric/sign forms conservatively fall back. A redundant leading “No,” is handled only when the remaining clause and canonical text independently carry negative polarity. An authored generic character status appears before local routing starts, so cold loading has immediate feedback. This is a practical rejection filter, not semantic verification. Unsupported relationships, omissions, source correctness, and subtle qualification changes still need evaluation. Malformed/failed/rejected phrasing returns the exact fallback and original sources. No result text gains action authority, shell access, or a second module invocation.

The [phrasing-polish pass](plans/0004-phrasing-polish.md) adds opt-in `--diagnostics`: safe typed phrasing categories/rejection reasons and timing go to stderr, without raw model replies, prompts, evidence, provider errors or persistent logs. Web fallback uses `Source [1] excerpt:` with a complete short sentence where possible, conservatively retaining common abbreviations/initials/acronyms; longer excerpts cut at a word boundary with an ellipsis. Profiles now live as one JSON file each under `profiles/`; CLI discovers them at startup, with `--profiles-dir` overriding the working-directory-relative default. `--personality ID`, `/ID` and `/profile ID` select any discovered profile. Duplicate/reserved IDs, malformed files and unsafe presentation text fail startup. Adding a valid custom file requires no source changes; restart reload is sufficient. Profiles contain instructions, greeting, generic status, opaque-capability progress overrides, optional templates and optional suffix/marker metadata; no profile-ID branches control presentation. Local profiles are trusted configuration, never action authority. Generated answers retain factual checks; authored template prose uses syntax/output-safety checks instead. The fixed generated style vocabulary can reject new character words; exact fallback and semantic-verification limits remain. Bundled convenience constructors support existing fixture examples; CLI uses file discovery. See [plan 0008](plans/0008-explicit-commands-and-profiles.md) and [ADR 0003](decisions/0003-explicit-commands-and-editable-profiles.md).

## Confirmed interaction direction

The chat interface is for brief task requests and answers. The user's expectation is that roughly 98% of interactions can be answered in one sentence; this is an experience target, not a hard output limit. Extended conversation is not the central feature. Personality should fit that brevity and responsiveness. The temperature example is a short lookup status followed by a concise factual answer in the selected style. Module-specific structured results alongside an answer are a possible later addition. The implementation keeps current-request context only; history and persistence are out of scope.

Progress text will be authored, with character- and module-specific variants. Final replies should take account of how the request was phrased, with a direct factual answer available as a fallback. Local Ollama reply generation uses the same configured model for routing and phrasing, with deterministic factual fallback. The default is the explicitly evaluated `qwen3.5:2b-q4_K_M`, selected on a small local fixture sample; cloud use is outside this milestone.

## Hardware and resource expectations

The compatibility target is a machine with 16 GB memory and no dedicated GPU. A hardware check during milestone setup found the current Mac is actually an Apple M1 Pro with 32 GiB memory (`hw.memsize = 34359738368`), superseding the user's approximate M1/16 GB description. Measurements here cannot establish performance on a base M1/16 GB machine. The user's main PC has 32 GB RAM and a GPU with 24 GB memory, but HEART must coexist with games and other applications. Its default should use modest resources. The measured 2B Q4 candidate was chosen over 4B for lower latency and memory in the original small evaluation. Later polish improved measured phrasing acceptance, but 2B still failed one of ten fixture routes and showed variable phrasing; 4B completed ten of ten in the final run at roughly twice the successful warm latency. Those small samples do not establish general accuracy. Models load on demand and unload after configurable idle, initially five minutes. Different explicit model choices per machine are supported; no automatic switching or resource scheduler is selected. Original Linux ARM64 fixture tests passed; polish tests were run on macOS. Live Linux inference and gaming coexistence remain untested.

## Agent configuration

`.codex/config.toml` requests `gpt-6.1-sol` with medium reasoning for the architect and enables agents. `max_concurrent_threads_per_session = 2` caps concurrent spawned-agent threads, excluding the primary thread: up to three total threads. Its subagent defaults request `gpt-6.1-sol` with medium reasoning. Only two custom roles are defined: `.codex/agents/developer.toml` and `.codex/agents/reviewer.toml`. Their instructions describe responsibilities; model and effort fields are deliberately omitted so selection can match the task.

Task selection policy:

- Architect: normally `gpt-6.1-sol`, medium reasoning; high for significant architectural decisions.
- Developer: normally `gpt-6.1-sol`, medium reasoning; use `gpt-6-luna`/medium for small, well-defined changes. Use Sol/high for difficult debugging or complex logic.
- Reviewer: normally `gpt-6.1-sol`, medium reasoning; high for security-sensitive or architecturally significant changes.
- Use Luna/low for straightforward documentation and formatting. Reserve Astra/medium or high for exceptional problems where Sol is struggling. Use Extra High (`xhigh`) only when a demonstrated quality benefit justifies the additional work. Prioritize responsiveness and implementation quality.

High-effort escalation is explicit task selection, not a fixed role-file override; all shared defaults are medium. Keep handoffs and tool output short, focus correction reviews on changed areas and affected behavior, and avoid extra agent calls for routine bookkeeping. Independent implementation review remains required. Revisit these preferences against the supported catalog when the environment changes. Never silently substitute an unsupported model or effort.

When a custom-role selector is exposed, select the role through that interface and explicitly request the appropriate model and effort. Custom role-file model/effort fields would override both spawn selections and shared defaults, which is why these files omit them. Explicit spawn selections override shared defaults.

The user reports successful native project role selection in a fresh session through `agent_type`, with the project instructions loaded natively. Prefer that mechanism when exposed and explicitly select the task's model and effort. Inspect the current session's tools rather than assuming every client exposes the same interface.

The original setup session exposed `collaboration.spawn_agent` without a custom-role selector. For interfaces with that limitation, use a fresh agent (`fork_turns="none"`), explicitly request the model and effort, and supply the relevant role TOML instructions together with a bounded task and instructions to read the repository sources. In that interface, full-history forks inherit the parent's model and effort and cannot accept overrides. Do not assume a role name in a task name loads its instructions.
